# ClipCargo 最终优化方向

版本：v1.0
制定日期：2026-11-27
适用项目：ClipCargo

本文是后续开发的唯一架构和产品优化基准。后续修改、拆分和重构都以本文为准，避免同一问题出现多个互相矛盾的方案。

## 1. 目标和范围

ClipCargo 的产品定位仍然是：

> 本地优先的网页视频收集、下载、素材整理、播放和基础处理工具。

本阶段的目标是：

- 借鉴 Concat 的工程分层和专业桌面软件设计方式。
- 保留 ClipCargo 当前的产品定位和已有能力。
- 优化代码可维护性、任务可靠性、UI 一致性和设置页信息组织。
- 为将来的批量处理、更多媒体能力和自动化接口预留边界。

本阶段明确不做：

- 不加入去水印功能。
- 不复制 Concat 的代码、品牌、图标或界面资源。
- 不把 ClipCargo 改造成非线性时间线编辑器。
- 不引入 React、Vue 等前端框架。
- 不立即重写现有数据库。
- 不为了架构重构改变当前用户工作流程。

## 2. 最终技术路线

最终采用以下技术路线：

```text
Tauri 桌面窗口
├── 原生 JavaScript / CSS 前端
├── Rust 后端
├── SQLite 本地数据
├── FFmpeg / FFprobe / yt-dlp / Deno 工具链
└── Chrome 扩展 Native Messaging 桥接
```

保留现有技术栈，主要调整模块边界，不进行技术栈替换。

## 3. 需要借鉴 Concat 的工程思想

Concat 的专业性主要来自以下几条原则：

### 3.1 核心业务不依赖界面

素材、任务、项目、处理参数和状态属于业务层，不应该由 HTML 元素或页面事件决定。

```text
界面只负责展示和发起操作
业务层负责决定操作含义
媒体层负责执行媒体操作
存储层负责保存状态
```

### 3.2 操作应该是明确的业务对象

不要让按钮直接控制复杂的 FFmpeg 细节，而是先形成明确的操作对象：

```text
MediaOperation
├── operation_type
├── input_asset
├── parameters
├── output_policy
└── created_at
```

当前操作包括下载、兼容 MP4、截取、提取音频、裁剪、旋转、静音、倍速和压缩。

### 3.3 窗口、扩展和未来 CLI 使用同一套应用能力

最终目标：

```text
Tauri UI
浏览器扩展
未来 CLI / 自动化
        │
        ▼
ClipCargo Application API
        │
        ▼
业务服务和任务调度器
```

目前不要求马上增加 CLI，只要求新功能不要把业务逻辑写死在某一个界面事件里。

### 3.4 长任务统一使用 Job

下载、媒体处理、组件安装都属于任务，统一拥有：

```text
id
kind
status
stage
progress
parameters
created_at
updated_at
error
cancel
output
```

现有下载任务和媒体派生任务先保持数据库兼容，先在代码内部统一任务处理方式；只有现有表无法支撑新需求时，才进行数据库迁移。

## 4. 最终目录结构

以下是最终采用的目标结构。此前出现的其他目录图均视为讨论过程中的参考，不再作为独立方案。

├── api/
│   └── tauri.js               所有 Tauri invoke 封装
├── state/
│   ├── store.js                全局状态
│   ├── preferences.js          用户偏好和 localStorage
│   └── selectors.js             状态查询和派生数据
├── views/
│   ├── inbox.js                 收集箱
│   ├── tasks.js                 任务
│   ├── library.js               素材库
│   ├── settings.js              设置
│   └── browser.js               浏览器和扩展状态
├── components/
│   ├── button.js                按钮和图标按钮
│   ├── tooltip.js               问号帮助提示和工具栏提示
│   ├── select.js                自定义下拉框
│   ├── dialog.js                弹窗和焦点管理
│   ├── status-pill.js            状态标签
│   └── media-card.js             素材卡片

说明：这不是要求一次性建立所有文件。实施时按模块逐步迁移，最终结构以此为准。

### 4.2 Rust 后端目录

```text
src-tauri/src/
├── main.rs                      启动、初始化和 Tauri 注册
├── app_state.rs                 AppState 和共享运行状态
├── commands/
│   ├── inbox.rs                 收集箱 command
│   ├── download.rs              下载 command
│   ├── media.rs                 媒体处理 command
│   ├── projects.rs              项目 command
│   ├── components.rs            工具安装和版本 command
│   └── settings.rs              设置 command
├── domain/
│   ├── models.rs                领域模型
│   ├── jobs.rs                  Job、状态和进度模型
│   ├── assets.rs                素材模型
│   └── errors.rs                统一错误类型
├── storage/
│   ├── database.rs              数据库连接和事务
│   ├── migrations.rs            数据库迁移
│   └── repositories.rs          数据查询和持久化
├── services/
│   ├── inbox_service.rs         收集箱业务
│   ├── download_service.rs      下载业务
│   ├── media_service.rs         媒体处理业务
│   ├── component_service.rs     工具安装和自检
│   └── project_service.rs       项目业务
├── workers/
│   ├── scheduler.rs              任务调度和并发控制

```

`main.rs` 最终不再承载数据库、下载、FFmpeg 和组件安装的具体实现，只负责组装应用。

## 5. 最终 UI 方向

Concat 的界面只借鉴设计原则，不复制具体页面。

### 5.1 整体风格

- 深色桌面软件风格。
- 面板边界清晰，但减少无意义的大卡片。
- 控件紧凑，减少重复说明。
- 主要操作使用单一蓝色强调色。
- 默认状态使用低对比度灰色。
- 激活、聚焦、悬停和禁用状态必须有统一规则。
- 优先使用图标和短标签，复杂说明放入 Tooltip。
- 主导航固定在左侧，设置分类固定在设置页左侧；不在顶部、底部和侧边之间切换位置。
- 不需要过度的文字注释。菜单只保留名称，只有会造成误解的操作才补充 Tooltip 或状态说明。

### 5.2 图标系统

继续使用现有 Lucide SVG 资源，但统一封装：

```text
14px  辅助信息
16px  工具栏和普通按钮
18px  导航和设置项
22px  主要功能入口
```

图标必须使用统一的颜色、线条权重、点击区域和激活状态。禁止在各个页面中自行决定图标大小和颜色。

### 5.3 Tooltip 系统

建立统一 Tooltip 组件，替代零散的原生 `title`：

- 工具栏图标按钮显示功能名称。
- 仅对不可见、危险或需要上下文的配置提供 Tooltip；普通设置不添加问号和重复说明。
- 支持鼠标悬停和键盘聚焦。
- 使用统一深色浮层、边框、圆角和最大宽度。
- 支持 `role="tooltip"` 和无障碍标签。

### 5.4 设置页

最终采用：

```text
左侧设置分类
        │
        ├── 通用
        ├── 下载
        ├── 工具
        ├── 浏览器扩展
        ├── 快捷键
        ├── 版本
        └── 关于
```

主导航与设置分类都保持左侧位置。右侧使用“设置名称 + 控件”的行式布局；只有复杂配置、安装流程和异常状态才使用卡片或说明。

### 5.5 文案与交互密度

- 菜单、按钮和设置项使用短标签，不在名称后附加解释性小字。
- 文案优先表达当前状态、结果和下一步动作，删除重复解释、营销句和把用户当新手的提示。
- 需要帮助时使用统一 Tooltip、帮助入口或错误状态，不把说明长期铺在主界面上。
- 设置分类支持鼠标、键盘方向键、Home/End 切换，并保持当前分类记忆。

### 5.6 版本和工具自检

设置页需要清楚展示：

- ClipCargo 当前版本。
- 浏览器扩展版本和通信状态。
- yt-dlp、FFmpeg、FFprobe、Deno 的版本和状态。
- 最后一次自检结果。
- 检查更新按钮。
- 工具安装位置。
- 许可证和第三方声明入口。

状态统一使用：

```text
正常 / 未安装 / 版本过旧 / 检查中 / 安装中 / 检查失败
```

## 6. Concat 工程实践中可以直接借鉴的部分

### 6.1 统一日志

后台任务、组件安装和媒体处理不要依赖零散的终端输出。应当有统一日志入口，并把日志写入用户数据目录。

### 6.2 依赖和模型清单

继续保留现有组件 manifest、版本读取、SHA-256 校验和失败回滚。未来所有可下载工具或模型都应有：

```text
名称
版本
平台
下载地址
文件大小
SHA-256
许可证
```

### 6.3 真实运行验证

发布验证不能只检查编译通过，还要验证：

- 打包后的程序能启动。
- 组件目录为空时能正确提示。
- 实际下载能运行。
- 实际媒体处理能运行。
- 取消、失败和恢复状态正确。
- 安装包中的扩展和资源完整。

### 6.4 接口契约

前端和 Rust command 的请求、响应、错误和事件需要逐步形成明确结构，避免只依赖字符串名称和临时字段。

## 7. 实施顺序

### 阶段一：建立边界，不改变功能

- 将 Tauri `invoke` 调用集中到 `src/api/tauri.js`。
- 将 `app.js` 中的状态、偏好、视图渲染和弹窗逻辑分组。
- 将 `main.rs` 按 commands、services、storage、media、bridge 拆分。
- 保持现有 command 名称和数据库表不变。
- 完成后运行现有前端检查和 Rust 测试。

### 阶段二：统一组件和设置页

- 建立图标封装。
- 建立 Tooltip。
- 统一按钮、下拉框、状态标签和弹窗。
- 把设置页改为左侧分类 + 右侧设置行。
- 增加版本、工具自检、扩展状态和关于信息。

### 阶段三：统一任务模型

- 抽取 Job、状态、进度和取消模型。
- 统一下载和媒体处理的调度逻辑。
- 用事件更新替代部分固定轮询，但保留轮询作为恢复机制。
- 增强失败、重试、取消和应用重启后的恢复。

### 阶段四：质量和发布工程

- 增加统一日志。
- 增加打包后启动和核心流程 smoke test。
- 固定外部依赖版本和 SHA-256。
- 增加版本兼容和数据迁移测试。
- 发布前核对源码、版本、安装包、扩展和许可证清单。

## 8. 验收标准

本轮优化完成后，应满足：

- 新功能不再直接堆进 `main.rs` 或 `app.js`。
- 前端、业务、媒体执行和存储之间有明确边界。
- 下载、处理和组件安装都有统一的任务状态表达。
- 设置页的 Tooltip、下拉框、按钮、状态标签样式统一。
- 用户可以在设置页看到版本、自检和工具状态。
- 现有浏览器扩展、下载、素材库和媒体处理功能不回归。
- 修改后可以通过已有检查，并完成实际桌面端验证。

## 9. 新对话使用说明

后续新建对话时，直接说明：

> 请先阅读 `docs/OPTIMIZATION-DIRECTION.md`，以此作为 ClipCargo 本轮重构和 UI 优化的唯一基准。不要加入去水印，不要引入 React/Vue，不要创建第二套互相冲突的目录方案；先检查当前代码，再按本文的阶段顺序执行，并在修改后验证。
